# 进度记录与 AI 交接

本项目用 GitHub Issue + Milestone + Project 记录动态进度。这样成员和不同 AI 会话看到同一状态，避免 README、聊天记录和个人清单互相冲突。

## 信息放在哪里

| 信息 | 唯一维护位置 | 不应放在哪里 |
|---|---|---|
| 任务状态、阻塞、负责人 | GitHub Issue 与 Project | `AGENTS.md` 的静态清单 |
| 截止日期、阶段验收 | GitHub Milestone | 聊天中的临时承诺 |
| 当次实施与测试证据 | Issue/PR 评论 | 仅保存在本地终端输出 |
| 架构、安全和接口规范 | `docs/` | 仅写在 Issue 评论 |
| 原始实验数据 | `data/raw/`，并在 Issue 标注条件 | 手工修改后的图表文件 |
| 阶段概览 | `README.md` | 逐日重复维护的任务表 |

## 看板状态定义

| 状态 | 进入条件 | 离开条件 |
|---|---|---|
| Backlog | 已记录，但近期不开始或输入不完整 | 输入和前置条件明确 |
| Ready | 范围、前置任务和验收标准清楚 | 成员开始实际工作 |
| In Progress | 已有人负责并正在修改或实验 | 产生可复核结果，或被阻塞 |
| Review | 代码/文档已完成，等待另一成员复核 | 复核通过或退回修改 |
| Test | 需要主机、逻辑分析仪或硬件验证 | 验收证据齐全或测试失败退回 |
| Done | Issue 验收标准全部满足且证据已链接 | 通常不再移动；回归问题建新 Issue |

无法继续时给 Issue 添加 `blocked` 标签，并写清：阻塞原因、影响、解除条件、可并行工作。`blocked` 是标签，不用它掩盖当前所处的流程状态。

## 防止重复工作的启动检查

开始任何任务前：

- [ ] 找到并认领对应 Issue；没有 Issue 时先建立工作项。
- [ ] 阅读 Issue 最近评论、关联 PR、前置任务和 Milestone。
- [ ] 搜索相同模块、关键词、文件名及开放 Issue。
- [ ] 检查本地分支、未提交改动和远端最近提交。
- [ ] 在 Issue 留下计划修改的文件、预期产出和建议负责人角色。
- [ ] 确认没有另一成员正在修改同一硬件接线或代码区域。

## Issue 更新模板

开始工作时：

```text
开始：YYYY-MM-DD
负责人角色：role:hardware / role:firmware
本次范围：
计划修改/测试：
前置条件：已满足 / 缺少……
预计证据：文件、CSV、逻辑分析仪截图或测试输出
```

暂停或阻塞时：

```text
当前结果：
阻塞原因：
影响范围：
解除条件：
现在可并行的任务：
最后相关提交/数据：
```

完成或交接时：

```text
完成内容：
提交/PR：
执行的检查与结果：
证据位置：
验收标准：满足 / 未满足（逐项说明）
仍未验证：
下一步：
建议看板状态：Review / Test / Done
```

## 每日与每周节奏

每个工作日开始时，两名成员只选各自一个主要 Issue，并确认是否存在共同硬件依赖。结束前用上述模板更新 Issue，即使当天没有完成，也要留下最新证据和明确下一步。

每个里程碑截止日前复核：

- 所有 `In Progress` 是否仍有人负责；
- `blocked` 项是否写明解除条件；
- 已关闭 Issue 是否真的有验收证据；
- `docs/open-questions.md` 和 `docs/risk-register.md` 是否反映新发现；
- 原始 CSV、测试条件和固件提交是否能够互相追溯；
- 未完成安全前置条件时是否已顺延测试，而不是压缩步骤。

不使用主观“完成 80%”代替可验证状态。一个任务要么仍有明确剩余验收项，要么证据齐全后进入 `Done`。
